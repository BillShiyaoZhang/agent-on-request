# Exhibition operator guide

For the dual-Hermes deployment with persistent KG-plugin data, follow [Docker setup](hermes-docker-demo.md). The audience uses `/` and the operator uses `/console`. The console's role-specific native-management links open each KG-plugin workbench and Hermes Dashboard. Use KG-plugin to edit the starting graph, calendar, availability and brief. Use Hermes to edit that role's skills, model and tools. Start a new audience round after saving changes so it captures the current native records and enabled skills.

The native workbench and the demonstration read the same role-local KG storage. Initialized rounds retain their own session/epoch snapshot. Preview leaves the recipient store unchanged. Once the receiver confirms delivery, its exact approved content is recorded in that round's native KG and becomes visible in the audience summary. A narrowed Bob approval writes only the selected fields to Alice's received records. Open **View collaboration trace** on the summary to inspect the persisted result, agent updates and receipt provenance. Native KG business records persist independently of the optional research-recording choice.

The instructions below also describe the standalone local-process mode. Its reusable fixture editor remains available when the native KG services are absent.

Use Node.js 26 or newer for the isolated Agent runtime. Production uses built-in Node modules and has no npm dependencies. Launch the app from the repository root:

```sh
npm run demo
```

Open the audience demo at [http://127.0.0.1:4327/](http://127.0.0.1:4327/) and keep the [operator console](http://127.0.0.1:4327/console) in a separate tab or on a separate operator screen. The local console opens without a PIN. It loads `MINIMAX_TOKEN_PLAN_KEY` from the Git-ignored `.env`. `DEMO_PORT` changes the local demo port. The `npm start` event mode uses port `4317` by default and requires the researcher PIN on `/console`.

```sh
AGENT_DEMO_ADMIN_PIN='a-dedicated-demo-pin' npm start
```

The default participant mode uses Guided/Controlled local Alice and Bob processes with synthetic stores. This path executes real signed ontology dialogue, mapping transformations and disclosure/receipt checks using deterministic planners. `npm test` runs the implementation checks. Configure Live mode in the researcher's Model configuration panel: the default is MiniMax China Token Plan with `MiniMax-M3`, separate Alice/Bob settings and a shared server-held subscription key. Enter the key and click **Save API key** beside its field (or press Enter); this saves just the key and preserves other draft settings. Validate, review and save any model parameter changes separately, then test each saved role before starting a new Live round. If changing the provider or URL, validate and save that connection and its key together using **Save for new rounds**. Existing rounds keep their original model snapshot. Read [minimax.md](minimax.md) for credentials, request format and the local process isolation boundary. The local demo loads `MINIMAX_TOKEN_PLAN_KEY` from the ignored `.env` automatically; key-source markers preserve explicit clear decisions. Optional PIN event mode retains first-run environment initialization. The participant page shows the model/traffic disclosure. A live provider error is a visible failure, not an automatic switch to controlled mode.

Choose Live for a model-assisted ontology dialogue. The interface automatically begins every new Controlled/Live round with alignment review; there is no separate review toggle. Only compatibility API callers omitting `alignmentReview` can use a known Guided mapping for an unambiguous quick start even when later meeting planning is Live. A provider connection probe checks connectivity only; it is not proof that the reviewed alignment and brief path will complete at conference time.

New model configurations default to `retryLimit: 1`: each planning request can make at most two provider calls for that role. Network failures/timeouts and proposal format/semantic corrections share that total budget. A saved explicit zero is respected and permits one call. Incomplete mapping acceptance is an invalid proposal to correct, not a person's refusal. A recognized ontology `reject`/`none` ends the model attempt as a refusal even if its explanation is missing, blank or too long, its identifiers are malformed, or it includes extra fields. Only a bounded explanation or fixed refusal message remains, and selected mapping IDs are cleared. It is never corrected into acceptance; accepting proposals still require full validation. A failure after the budget is exhausted identifies the failed step and a fixed safe explanation. It never switches to Guided automatically.

## Local rehearsal

Before admitting a participant, rehearse these paths using research consent off:

1. In the native deployment, open each role's KG-plugin workbench and Hermes Dashboard from the console. Inspect the starting data and enabled skills there, then start a new audience round. In standalone mode, open **Initial KG and skills**, edit each agent, validate the draft and save the default. Existing rounds retain their original initialization.
2. Start a Guided round; alignment review appears automatically. Inspect selected interval/status modules, weekday and minute conversion, and the task-scoped Free correspondence. Accept and confirm the signed peer dialogue completes before data sharing.
3. Start the ambiguous scenario. Request clarification; verify no mapping/facts are accepted yet. Confirm the meaning for this invitation, then try a separate rejected-alignment round. A rejection must complete with an alignment-specific explanation, without sending a calendar snapshot.
4. Preview Tue–Wed free slots. Confirm the preview does not populate Bob's receipt store. Send once and check the approved hash matches the received hash and semantic facts reference the accepted mapping version.
5. Add only the requested free slots. The default requests Thursday; change Bob availability to Friday in another synthetic round and check the request follows that date. Confirm Bob receives no titles/notes and can use the mapped common interval.
6. Decline an initial sharing request and an additional sharing request in separate rounds. Compare their explanations with a no-common-time fixture; these must not all be described as rejection.
7. Where Bob's optional brief needs permission, use **Review Bob approvals** in the console. Confirm closing the approval leaves it pending, narrowing to topic excludes agenda, and denying it preserves an already arranged meeting. The brief has a separate semantic task module.
8. Check that the audience summary shows the result and an expandable collaboration trace. Open the trace to check both the agents' messages and confirmed receipts. Alice can inspect her own state and confirmed exchanges.
9. Withdraw Alice's future sharing. Confirm the existing Bob receipt and semantic provenance remain visible and subsequent sharing is blocked.
10. Disconnect Bob, restore connectivity and then explicitly retry. Confirm restoration itself does not disclose anything. A retry must reuse the same approved operation and cannot duplicate a receipt or widen the payload.
11. Test reviewed Live alignment with a valid model result, a none/rejection result and a technical failure. Failure must stay visible; switching to Guided requires an explicit new round.
12. End the round on the audience screen, then start a new one. Confirm a fresh epoch/token, both stores initialized from the current default, the prior token rejected and research consent off.
13. Finish one explicitly consented v2 rehearsal and inspect its research timeline and export. Step through selected modules, mapping decision, actual reception, narrowed approval and revoked state; confirm semantic facts link to receipt/mapping versions, ontology safe export survives reload, expired permissions retain the recorded timestamp and credentials/raw provider messages are absent. Keep rehearsal collection separate from participant data. Deleting a rehearsal currently requires trusted operator maintenance through `ResearchStore.deleteRun()`; there is no research-panel deletion button or HTTP delete endpoint.

## Initial conditions and visible state

Follow the participant page from the main collaboration flow into optional detail. First inspect the concept differences and task module in the automatic alignment review. Explain Alice's `{day,time,status}` versus Bob's `{weekday,startMinute,endMinute,bookable}` using the concrete conversion card. For ambiguous Free, let the person explicitly confirm or decline invitation meaning. Then choose a separate sharing scope, preview the exact information and confirm only what may be sent. The **Information Alice received** card appears only after a confirmed Bob-to-Alice receipt and shows actual received values; a pending approval is not received information. Narrowing a Bob approval keeps excluded fields out of that card.

A plain explanation of the alignment card is: “The assistants agree how to read a date, a time and the word Free.” Alice's Tuesday clock range must become Bob's weekday number and minute values. An empty calendar alone may not mean the owner wants an invitation. Accepting that interpretation does not send calendar data; the person still chooses the exact sharing preview afterward.

When a participant wants more context, open Alice's optional details to inspect her calendar, knowledge, skills and permissions. Use receipt details for the exact fields actually received. The console uses the researcher observer view to inspect a selected round. Opening a graph, card or receipt leaves permissions and delivery unchanged.

Choose a complete preset or compose each agent's KG, data, skills and authorization components. There is at most one component per category per role. Custom JSON patches apply last; arrays replace the selected array. The from-scratch preset starts with empty data/graphs/skills/scopes and still requires complete, validated synthetic conditions before running. Invalid time intervals, duplicate graph IDs, missing edge endpoints, wrong-role registered skills/components and credentials are rejected. Safe custom skill labels are metadata; they do not create new runtime actions. The catalog and JSON Schema are served by the backend, and the preview uses the same resolver as session creation.

In native KG mode, use the corresponding native workbench to edit either agent's initial KG and data, and Hermes Dashboard for skills. The next round reads these stores and freezes its initialization. In standalone mode, **Save as demo default** applies the reviewed console fixture to new rounds. Restore the built-in conference preset if you want future rounds to follow the current Bob owner template. Standalone API integrations that explicitly override Bob's starting conditions in PIN mode send `X-Researcher-Token` with the researcher credential and retain the participant token for any previous-session replacement.

Review the graph and category cards inside the optional Alice and Bob sections during a round. Own knowledge and confirmed received knowledge have distinct origins; a received node carries receipt provenance. Bob cannot gain Alice's private rows or initial KG through the state visualization. Initial KG enters only its owning model context. Each agent's skills card reflects its actual current configuration, and authorization cards expose allowed fields/dates, budget consumption, remaining uses, expiry and owner-review requests. Alice read/preview/send skills and field/date/usage/expiry limits are enforced in the runtime as well as the controller. Taking a preview consumes no send budget; allocating an authorized transmission consumes a use even if receipt confirmation is delayed.

The initialization workbench shows both fixtures so an operator can construct a synthetic experiment. Describe it as configuration/observation, not the Alice owner's access to Bob's real private assistant. Separate three statements throughout the demonstration: “we agreed on meaning,” “an owner permitted this exact disclosure,” and “the recipient confirmed receipt.” A mapping can succeed while sharing is refused. A received snapshot can be insufficient to interpret eligibility. A completed meeting does not imply sharing titles, notes or a complete brief.

The reference task is 30 minutes. The task selector also supports 45 and 60 minutes; the API additionally accepts 15 minutes. Longer tasks need intervals that actually contain that duration. Event titles and notes are outside the scheduling working subset. The result should identify which module/mapping resolved an interpretation problem and which scoped content arrived, rather than treating all successful meetings as evidence of broad access.

## Researcher's controls

Local demo controls are available directly. The optional PIN event mode uses sign-in. Access to these controls does not create any Alice sharing permission.

The operator console starts with links to agent defaults, connection cards for Agent Comm A and B, and the selected round's submitted action, confirmed receipts and outcome. Open the session switcher when changing rounds. Pause and resume, Bob approval and Bob configuration act on the selected round. Connection simulation, retries, injected requests, technical identity and exact receipt JSON are optional sections. In Hermes direct mode the cards show both local TCP listeners. The regular runtime uses process IPC and shows the direct endpoints as inactive.

The Bob owner template supplies built-in starting conditions. A saved demo default supplies its own resolved KG, skills, data and authorization to new rounds. A session-targeted Bob apply pauses the selected round at a safe point, supersedes changed pending Bob approvals and rechecks the new policy before resume. Received snapshots are immutable. A saved profile stores reusable configuration separately from research records.

Review the validation errors and diff before apply. Unknown ordinary config keys survive editing, saving and reload. Keep `data.synthetic: true` and use legal `{day,time}` availability objects. Custom capabilities are configuration names; only registered executor capabilities can run. Never paste personal Agent stores, real API keys or private calendars into this demonstration.

One-time approval authorizes one exact Bob action. The review shows the recipient, purpose, reason and actual field values before the decision. Unchecking a field excludes it from the approval while leaving its pending value visible for comparison. Round approval and its use/expiry settings are available in an optional section; the grant is bounded by current recipient, resource, purpose, selected fields and exact values, uses, expiry and session. It does not automatically broaden a Bob template. Field selection can narrow a pending payload; it cannot add unsupplied fields. A changed policy revision or payload requires renewed review.

Recovery operations have distinct meanings:

| Control | Effect |
|---|---|
| Pause / resume | Stop scheduling and continue after policy/state checks |
| Disconnect / restore Bob | Change transport availability; restoring does not send |
| Retry | Reconcile/reuse an existing approved operation |
| Inject request | Explicit researcher intervention, marked in consented research metadata |

When model planning fails, inspect the displayed step and safe reason before explicitly resuming or retrying. A model correction requests a fresh proposal; a delivery retry reconciles the same already-authorized operation and payload. Neither creates a new disclosure grant. Keep confirmed received snapshots and their provenance visible during recovery; do not restart simply to hide a failed model step. If the participant chooses Guided instead, start a new round explicitly and keep the mode change identifiable in any consented research interpretation.

After a meeting has actually been confirmed, a failed optional Bob brief proposal or briefing alignment also offers **Keep the meeting and skip optional context**. The participant can finish as `arranged` with that exact confirmed meeting, without another model call, brief delivery or authorization use. The action cancels the unfinished optional brief and its pending approvals while keeping receipt history. It applies only to a pause at `bob_brief` or `brief_alignment`; an unconfirmed meeting, another pending delivery, a stopped-sharing round or Replay cannot use it to create success.

## Both Agents on this computer

The event app always runs Alice and Bob locally; a legacy `BOB_URL` is ignored. Workers have independent private working directories and contexts, and Node permissions deny direct network access, filesystem writes, child processes, threads, addons and Inspector access. Only their registered runtime code is readable. They do not receive provider credentials. This restricts the known Worker implementation; it is not a hostile-code OS sandbox. The parent model broker makes Live requests to the configured provider, so local Agent processes do not imply a local LLM. Read [runtime.md](runtime.md) for the harness and lifecycle.

Use the papers as research motivation, with the bounded adaptation explained in [ontology-dialogue.md](ontology-dialogue.md). Guided executes actual signed dialogue and mapped data exchange; it is appropriate for the main conference path. Live adds independently reviewed candidate selection. Neither mode reproduces unrestricted ontology matching, the original benchmark experiment, independently administered machines or a formal privacy guarantee. Conditional correspondence and owner clarification are extensions for this demonstration.

## Collecting and ending a round

Research consent is optional and independent from Alice sharing. Give participants the approved information before asking for consent. New `research-v2` collection records event metadata and complete fictional state: initial KG/data/skills/scopes, calendar and brief values, receipts, owner approvals, grants and use counters. It excludes participant/admin credentials, model keys/endpoints, configuration prompts, raw chat and reasoning. Legacy `research-v1` records remain metadata-only and are not expanded. Internal round and operation identifiers link steps; the records are pseudonymous, not completely anonymous. Record substantive assistance or an injected request as an intervention and keep admin waiting distinct from participant decision time.

Reaching a task outcome does not immediately close research collection: the optional scope, withdrawal, ontology-alignment and task-module understanding questions can still be answered. The first choice submits automatically. The page waits for server confirmation before showing the original answer alongside the expected boundary and its explanation; there is no second submit step. The first answer stays locked and is never replaced by the expected answer. If confirmation is lost, verify or retry the same original answer. Participants still receive this feedback with research consent off, but no research answer is stored. Consented records preserve the original answer and its recorded correctness; a missing answer is not treated as an incorrect answer. These checks follow explanation and do not establish blinded learning gains or privacy preferences.

The summary distinguishes task outcomes from runs awaiting an explicit End. At the end of a round inspect its outcome, end/reset it, and verify that the next person starts with a fresh session. Avoid collecting research data from replay; replay is explanation material. Export actual records from the authenticated research panel as JSONL or CSV; JSONL retains each complete run and is preferable for detailed reconstruction. Persisted traces allow later review, including after restart, but cannot restart the original agents. A broken trace hash chain is marked `trace_integrity_failed`, and an open run interrupted by restart becomes `incomplete + process_interrupted`. Keep rehearsals, altered configurations and assisted rounds identifiable for analysis. Read [research.md](research.md) for the exact recording gate and analysis rules.
